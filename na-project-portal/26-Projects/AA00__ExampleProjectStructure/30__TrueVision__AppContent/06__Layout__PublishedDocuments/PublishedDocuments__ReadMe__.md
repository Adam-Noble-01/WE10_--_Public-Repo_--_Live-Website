# Published Documents — folder shape

**This folder is a worked dummy example, not a real project.** It exists so the shape of
a published drawing can be read and argued with. Every file in it is hand-made with
plausible values. Nothing here is generated by the app.

**Written 23-Sep-2026. Adam Noble — Noble Architecture.**

---

## ⚠ THIS FOLDER IS THE SCHEMA. KEEP IT IN PARITY WITH THE CODE.

**To whoever changes a published data structure next — agent or human — read this first.**

This is not a sample output that can be left to rot. It is **the readable form of the
published-document schema**, and it is the template Adam looks at to see the shape of a
published drawing for every job. It is deliberately here, in the project portal, and not
in the TrueVision app tree, because it is a *document* about documents.

That location is also the danger: **nobody changing the code will trip over this folder.**
So the link is written down at both ends.

| End | Where | What it says |
|---|---|---|
| Code | `na-apps/30__TrueVision__CoreAppCode/02__Src__AppModules/53__Data__Layout__PublishedSchema/README__PublishedSchema__.md` | Points here, and every file in the three publishing modules carries a `SCHEMA REF` header line pointing here too |
| Example | this file | Points there |

**The rule: a change to any published key, file name, folder name or tier is not finished
until this folder matches it.** Add a key to `Elements__Dimensions__.json` in code, add it
here. Rename a folder, rename it here. Change the tier ladder, change
`PublishedDocuments__Index__.json` here.

`Publish__SchemaVersion` is the check. It is in
`PublishedDocuments__Index__.json` here and in `Na__PublishedSchema__.json` in the code.
**If the two numbers differ, this folder is stale and the schema is undocumented.**

The plan that owns all of this is
`na-apps/30__TrueVision__CoreAppCode/TrueVision__PLAN__PublishingSystem__.md`, section 1.5.

## What this folder is for

`06__Layout__PublishedDocuments` holds the **baked** form of each drawing: the finished
document a reader on the live web downloads and looks at. In the app and to a client
this is called **publishing**; in the code it is called **baking**. The two words mean
the same event and the split is deliberate — "publish" is the button and the status a
client sees, "bake" is the file-making the code does.

**Authoring never reads this folder.** The Layout Editor on localhost goes on working
exactly as it does today, from `TrueVision__ProjectData__.json`. Publishing only ever
*writes* here. Nothing in this folder is ever a source of truth for authoring, and
deleting the whole folder loses no drawing work.

**The reader never reads anything else.** A drawing tab on the live web opens the
document in this folder or it opens nothing at all — see "Unpublished" below. There is
no fallback that computes a drawing on the reader's device, because that fallback is
what crashes phones.

## The document id is the folder name

`AA00_T02_D02` — project code, phase, drawing number. Exactly the identifier the title
block prints, and exactly the folder-naming convention `05__Layout__DrawingDocs__Images`
already uses for sheet pictures. It is composed on every read and never stored anywhere
(see `TrueVision__NOTES__DrawingNumberingSchema__.md`), so a renumber or a phase change
makes a **new folder** — and the old one is archived, not orphaned.

---

## Two things per viewport, and only two

A 2D viewport today is a stack: a raster underlay, an SVG linework overlay, a separate
raster depth-fog layer, and whatever the compositor weights on top. Published, it is:

| | What it is | Why |
|---|---|---|
| **One raster** | Every pixel layer of that viewport flattened into one opaque image — underlay, fog, enhancement, all of it already applied | One decode instead of two or three; no compositing; no premultiplied-alpha path, which is where the black viewports live |
| **One vector** | The projected linework as a paint-ready SVG: about five `<path>` elements with their stroke colour, width, opacity and dash already resolved | The reader needs no styling engine, no owner tags, no appearance rules — it needs an SVG |

**The raster is published at four sizes, not two formats.** A WebP and a PNG of the same
pixel dimensions cost exactly the same memory once decoded (`width × height × 4` bytes),
so swapping codec saves download and nothing else. What saves memory is **fewer pixels**.
The four tiers are in the index; `Tier01__Fit` is what loads when a sheet opens fitted to
the screen, and it is roughly fifty times smaller in memory than what the viewer decodes
today.

The print tier is a **PNG** because the PDF builder needs one (jsPDF drops the alpha of
raw RGBA) and because print is the one place lossless earns its bytes. Every screen tier
is WebP.

## One file per drawing element, named after its layer

The element files are not a new taxonomy. `Sheet__Layers` already carries a
`Layer__Type` of `annotation`, `dimension`, `vector`, `area`, `viewport` or `image`, and
that is the split, one file each. `Document__Sheet__.json` gives every layer a
`Layer__File`, so **a layer is a file**: a future show/hide in the reader loads or drops
one file, and never filters a list.

**The element files carry the authoring keys verbatim.** `Dimension__Id`,
`Annotation__PosXMm`, `Shape__Points`, `Leader__TipXMm` — unchanged, so publishing is a
splitter and not a translator, and a document can always be read back.

**Plus one resolved key wherever the authoring side computes something at paint time.**
This is the part that earns the whole design, because each of these is a module the
reader then does not need:

| Element | Added at publish | What it removes from the reader |
|---|---|---|
| Dimension | `Dimension__Text` — the finished string | The whole dimension-text maker: precision, units suffix, at-scale, round-up-to-5 and its asterisk. The reader can never print a number the drawing does not. |
| Floor area | `Area__LabelText` and `Area__AreaM2` | The area maths. m² is never stored in the project data — it is computed on paint. |
| Drawing title | `Title__UnderlineWidthMm` and the laid-out lines | The text-metric refit, which on the authoring side has to run twice because titles refit once the font loads. |
| Leader / bubble | `Leader__Text` already resolved, plus the spec note's text | The specification lookup. |

## Coordinates

Every published number is **paper millimetres in the authored space: origin top-left, x
right, y down** — the same numbers the project data holds and the same space the linework
asset already declares. Nothing is flipped at publish time.

`Paper__OriginCorner` and `Paper__AxisY` are written into `Document__Sheet__.json` so the
space is declared rather than assumed. A reader that wants CAD semantics — origin bottom
left, y up — applies **one transform to one group**, which is a matrix in the reader, not
a conversion of every number in every file. Flipping at publish time would mean every
element file, every SVG and every raster offset has to agree about the flip, and a single
disagreement is a silently upside-down drawing.

## Revisions

The revision lives on the document, not on the folder. Publishing compares the revision
being published with the one in the folder:

- **Same revision** — overwrite in place. No archive, no history. A revision is worked on
  until it is issued; keeping ten copies of an unissued Rev B is clutter.
- **New revision** — zip the existing folder to
  `00__Archive__Revisions/<document id>__Revision__<old>.zip`, then build the new folder
  clean.

The zip is made by the local server, not the browser — Python's `zipfile`, one call, and
no zip library to vendor into the app.

`00__Archive__Revisions` starts with `00__`, which is what keeps it local: the R2 sync
skips every folder whose name starts with `00__` (`SKIP_FOLDER_PREFIXES`), so archives
never reach the bucket and never reach a client.

**Only the latest revision is on R2**, for now. Past revisions exist on the authoring
machine and in the archive zips. If past revisions are ever wanted on R2 they go in a
sibling folder — the index already has room to name them.

## Publish order, and why it is this order

R2 keeps one live copy of each document and nothing else, so the purge has to be safe
against a publish that fails half way. The order is:

1. Build every file locally, into the document folder.
2. Upload every file to R2.
3. `HEAD` each uploaded key and check the byte count.
4. Write `Document__Manifest__.json`.
5. **Delete only the keys under this document's folder that the new manifest does not
   name.**
6. Write `PublishedDocuments__Index__.json` last of all.

The manifest is the atomic switch for one document and the index is the atomic switch for
the project. A publish that dies at step 2 leaves the previous document whole, because
nothing was deleted and no manifest changed. **The purge is scoped to one document's
folder, never to a prefix sweep** — a bucket-wide sweep on a partly-failed publish
deletes live drawings.

## Unpublished

A drawing that exists in the register but has no folder here is `unpublished` in the
index. The reader opens it as a **real sheet**: correct paper size, correct orientation,
the title block drawn and filled from the index. Inside the drawing area it puts a grey
mask and a line of text saying the drawing has not been published yet.

It does not attempt to load anything. It does not fall back to the authoring renderer.
That fallback is the crash.
